## 1. Problem statement

**Today:** No refund mechanism exists. `refunds` and `refund_lines` are still the empty spec 003
baseline skeletons — `refunds` carries only `id`, audit columns, `version` and `payment_id`; it has
**no** status column, and unlike `requests`/`offers`/`bookings`/`payments`/`payouts` it has **no**
`refunds_status_transitions` table and no status-transition trigger attached. Spec 021 shipped the
`PaymentProvider` adapter seam with `authorize`, `capture`, `voidAuthorization` and `getStatus` —
but **no `refund` primitive** — and deliberately left `captured → refunded` and
`captured → partially_refunded` unseeded in `payments_status_transitions` for this spec. Spec 020
likewise left every booking transition into `refunded` unseeded for this spec.

Master spec §49 requires full and partial refunds, both automatic policy-driven refunds and
admin-controlled overrides where permitted, with a `Requested → Processing → Completed/Failed`
status flow, reconciled against provider earnings, and fully audited.

**Who is affected:** Customers owed money back; providers whose earnings must reconcile correctly
against any refund; Finance Admins who approve overrides.

**Why it matters now:** It is the execution half of cancellation policy (023) and the deduction
input to payout reconciliation (024); neither can be correct without it.

**Success looks like:** A refund (full or partial) is executed through the **same** payment-provider
adapter spec 021 owns — never fabricated in application code, never reported complete without the
provider confirming it — can be issued automatically from an eligibility decision spec 023 supplies
or by a Finance Admin override through spec 009's existing approval framework, can never
cumulatively exceed what was actually captured, and leaves a durable, auditable reconciliation fact
for spec 024.

## 2. Acceptance criteria

AC-1 through AC-6 are preserved. AC-1 is re-grounded on the eligibility seam (§3 "Eligibility")
because spec 023 owns the policy; AC-3's approval threshold is resolved (§3 "Admin override");
AC-4's reconciliation is made a durable fact rather than an implementation this spec performs. AC-7
and AC-8 are added because without them provider ambiguity and concurrency — the two ways a refund
system loses money — are unspecified.

| # | Criterion |
|---|---|
| AC-1 | **Given** an authoritative refund eligibility decision supplied by spec 023 (§3 "Eligibility") **When** it reports `eligible` with an amount and reason **Then** the refund is created and executed with no manual intervention, moving `requested → processing → completed`, and spec 022 applies **no** cancellation-policy rule of its own |
| AC-2 | **Given** a partial refund **When** issued **Then** the exact amount and reason are recorded as immutable `refund_lines` rows whose amounts sum exactly to the refund's `total_amount_minor_units`, and the cumulative total of completed **and** in-flight refunds never exceeds the amount actually captured (§3 "Financial invariants", I-1) |
| AC-3 | **Given** a Finance Admin refund override **When** initiated **Then** it goes through spec 009's existing `authorizeAndInitiate()` on `(resource: 'refunds', action: 'override')`, which this spec seeds at risk tier **`high`** — so **every** override requires a second, distinct, authorized admin's approval before execution, with no amount threshold to define (§3 "Admin override"). No refund is executed while its `AdminAction` is `Pending` |
| AC-4 | **Given** a refund that the provider has confirmed **When** it reaches `completed` **Then** it durably records `reconciliation_state = 'pending'`, which is the fact spec 024 consumes to reduce the provider's earnings. Spec 022 implements no ledger, writes no `payouts` row, and never marks a refund reconciled; a refund awaiting reconciliation is still financially `completed`, and spec 024 must not report a provider "paid" for an amount carried by an unreconciled refund |
| AC-5 | **Given** a refund attempt on a payment whose captured amount is already fully refunded **When** attempted **Then** it is rejected `422 ALREADY_FULLY_REFUNDED`, and a request that would merely *exceed* the remaining refundable amount is rejected `422 REFUND_EXCEEDS_CAPTURED_AMOUNT` — neither is silently truncated, and neither reaches the provider |
| AC-6 | **Given** a **definitive** provider-side failure **When** it occurs **Then** the refund becomes `failed`, releases its reservation against the remaining refundable amount, records the provider's failure code, emits the notification port's `refund_failed` event, and is retryable by creating a new refund with a fresh `Idempotency-Key` |
| AC-7 | **Given** a provider call that times out or returns an unknown outcome **When** it happens **Then** the refund stays `processing` — **never** `failed` — its reservation stays held, no second provider call is made for it, and the reconcile sweep resolves it by calling `getRefundStatus(providerReference)` until the provider reports a definitive outcome (master spec §132.7: never claim an outcome the provider has not confirmed, in either direction) |
| AC-8 | **Given** two concurrent refund requests against one payment whose amounts together exceed the remaining refundable amount **When** both are submitted **Then** exactly one is accepted and the other is rejected `422 REFUND_EXCEEDS_CAPTURED_AMOUNT` — serialized by a `FOR UPDATE` lock on the `payments` row, not by an application-only read-then-write check; and the same `Idempotency-Key` submitted twice produces exactly one refund |

## 3. API contract

### What this spec reuses rather than re-inventing

| Need | Existing mechanism reused | Not created |
|---|---|---|
| Talking to the payment provider | spec 021's `PaymentProvider` in `lib/payments/provider/`, **extended** with one `refund` primitive (below) | a second payment abstraction |
| Payment state | spec 021's `payments` row and `payments_status_transitions`; this spec seeds only the three refund transitions spec 021 reserved | a parallel payment record |
| Booking state | spec 020's `applyBookingTransition()` with `actorRole: 'system'` | any direct `bookings.status` SQL |
| Status-machine enforcement | spec 003's generic `enforce_status_transition()` function, by creating `refunds_status_transitions` and attaching the trigger | a new trigger function |
| Admin approval | spec 009's `authorizeAndInitiate()` / `decideAction()` / `executeApprovedAction()` and its audit log | a second approval system |
| Approval listing/decision routes | spec 009's existing `GET /admin/approvals/pending` and `POST /admin/approvals/{actionId}/approve|reject` | a refund-specific approval route |
| Idempotency | spec 015's `requireIdempotencyKey()` / `idempotencyFingerprint()` in `lib/api/idempotency.ts` | a second idempotency scheme |
| Rate limiting | spec 004's existing `payment` domain (10 / 60s) | a new rate-limit domain |
| Background execution | spec 021's Vercel Cron pattern (`app/api/v1/cron/*`, bearer `CRON_SECRET`) | a new scheduler |

**The draft's `GET /api/v1/admin/refunds/pending-approval` is removed.** Spec 009 already ships
`GET /api/v1/admin/approvals/pending`, which lists every `Pending` `AdminAction` the caller is
authorized to decide — refund overrides included, because they are ordinary `AdminAction` rows.
Adding a refund-specific listing would be a second approval surface.

### Provider seam extension (AC-6, AC-7)

Spec 021's `PaymentProvider` has no refund primitive. This spec **extends that interface** —
`lib/payments/provider/types.ts` — rather than introducing a parallel one, and the sandbox adapter
gains the matching implementation. `lib/payments/provider/` remains the only directory permitted to
hold provider credentials, and spec 021's `no-fabricated-success.test.ts` guard is extended to cover
refund statuses on the same terms.

```typescript
// lib/payments/provider/types.ts — ADDED by spec 022
export interface RefundInput {
  idempotencyKey: string;
  /** The authorization/capture handle spec 021 stored on the payment. */
  providerReference: string;
  amountMinorUnits: number;
  currencyCode: string;
}

/** ADDED to spec 021's existing ProviderOutcome union. */
export type ProviderRefundOutcome = 'refunded' | 'failed' | 'unknown';

export interface ProviderRefundResult {
  outcome: ProviderRefundOutcome;
  /** The provider's own handle for THIS refund, distinct from the payment's reference. */
  refundReference: string | null;
  failureCode?: string;
  failureMessage?: string;
}

export interface PaymentProvider {
  // ... spec 021's authorize / capture / voidAuthorization / getStatus, unchanged ...
  refund(input: RefundInput): Promise<ProviderRefundResult>;
  /** Reconciliation read for AC-7's ambiguous case. */
  getRefundStatus(refundReference: string): Promise<ProviderRefundResult>;
}
```

`'unknown'` is the load-bearing value: it is what a timeout, a dropped connection or an
unrecognised provider response maps to, and it is **never** collapsed into `'failed'`. AC-10 of
spec 021 still applies unchanged — a sandbox adapter cannot run under `NODE_ENV=production`, so no
refund can be "confirmed" in production by an adapter that moves no money.

### Refund lifecycle (AC-1, AC-6, AC-7)

```
requested ──► processing ──► completed
                 │
                 └────────► failed
```

`requested` and `processing` are both **in-flight** and both hold a reservation against the
remaining refundable amount. `completed` and `failed` are terminal; neither has an outgoing
transition in this spec. There is deliberately **no** `processing → requested` and no
`failed → processing`: a retry after `failed` is a **new refund row** with a fresh
`Idempotency-Key` (AC-6), never a resurrection of the failed one, so every provider attempt keeps
its own immutable record and its own provider reference.

Enforcement uses spec 003's existing mechanism: this spec creates `refunds_status_transitions`,
seeds exactly the three pairs above, and attaches the **existing** `enforce_status_transition()`
function as `refunds_status_transition_trg`. No new trigger function is written.

### Eligibility seam (AC-1) — spec 023 owns the policy

Spec 022 contains **no cancellation rule, no free-window arithmetic and no fee calculation.** Spec
023 computes them and supplies an authoritative decision. Because spec 023 does not exist yet, this
spec ships the **port** with an inert default — the same idiom spec 020 used for
`CompletionEvidenceGate` and spec 021 for `DisputeGate`:

```typescript
// lib/refunds/eligibility.ts
export interface RefundEligibility {
  eligible: boolean;
  /** Required and > 0 when `eligible`. In the booking's own currency. */
  amountMinorUnits?: number;
  currencyCode?: string;
  /** Required when `eligible` — recorded verbatim on the refund line, immutably. */
  reason?: string;
  /** The spec 023 decision this came from, stored for audit. Opaque to this spec. */
  decisionRef?: string;
}

export type RefundEligibilityGate = (tx: Executor, bookingId: string) => Promise<RefundEligibility>;
```

The shipped default returns `{ eligible: false }`, because no spec has defined a refund policy yet.
That is correct rather than a stub: with no policy, nothing is automatically refundable, and the
admin-override path (which does not consult this gate) remains fully usable.

**When eligibility is absent, stale, invalid or contradictory** — each case is decided, none is left
to interpretation:

| Case | Behaviour |
|---|---|
| Gate returns `eligible: false` | `422 REFUND_NOT_ELIGIBLE`. No refund row, no provider call |
| Gate returns `eligible: true` but omits `amountMinorUnits`, `currencyCode` or `reason` | `422 REFUND_ELIGIBILITY_INVALID`. A half-specified decision is a defect in the supplying spec, never a reason to guess an amount |
| `amountMinorUnits` ≤ 0, non-integer, or `currencyCode` ≠ the booking's | `422 REFUND_ELIGIBILITY_INVALID` / `422 REFUND_CURRENCY_MISMATCH` |
| `amountMinorUnits` exceeds the remaining refundable amount | `422 REFUND_EXCEEDS_CAPTURED_AMOUNT`. **Never truncated to fit** — silently refunding less than a policy decided is as wrong as refunding more |
| Gate throws, or no gate is registered | `422 REFUND_NOT_ELIGIBLE` with `details.reason = 'eligibility_unavailable'`. Never a default-allow |
| Decision is stale | The gate is consulted **inside the refund transaction, under the payment row lock**, immediately before the reservation is written. There is no window in which a decision read earlier can be acted on later, so staleness cannot arise from this spec's own timing |

### Financial invariants (AC-2, AC-5, AC-8)

All money is integer minor units in the booking's currency — spec 003 AC-1's convention, enforced
by `npm run check:schema-money-lint`. The authoritative captured amount is
`payment_authorizations.captured_amount_minor_units` (spec 021), **not** `bookings.price_amount_minor_units`
and **not** `payments.charge_amount_minor_units`: only the authorization row records what the
provider actually took.

Definitions, all scoped to one `payments` row:

| Term | Definition |
|---|---|
| `captured` | `payment_authorizations.captured_amount_minor_units`, `NULL`/absent ⇒ nothing is refundable |
| `completedRefunded` | `SUM(total_amount_minor_units)` over refunds with `status = 'completed'` |
| `inFlightRefunded` | `SUM(total_amount_minor_units)` over refunds with `status IN ('requested','processing')` |
| `remainingRefundable` | `captured − completedRefunded − inFlightRefunded` |

| # | Invariant |
|---|---|
| I-1 | `completedRefunded + inFlightRefunded ≤ captured`, always. **The cap is against both (a) the captured amount and (b) everything already completed or in flight** — expressed as this single inequality, so neither a burst of concurrent requests nor a long-running `processing` refund can open a gap |
| I-2 | A new refund is admitted only if `total_amount_minor_units ≤ remainingRefundable`, evaluated **after** taking `SELECT ... FROM payments WHERE id = $1 FOR UPDATE`, in the same transaction that inserts the row. This is what makes AC-8 structural rather than advisory |
| I-3 | `total_amount_minor_units > 0`. A zero-value refund is rejected `422 REFUND_AMOUNT_INVALID` — there is no justified zero-value refund in this spec; a "nothing is owed" outcome is `eligible: false`, not a zero refund |
| I-4 | Negative amounts are impossible: `CHECK (total_amount_minor_units > 0)` on `refunds` and `CHECK (line_amount_minor_units > 0)` on `refund_lines` |
| I-5 | `SUM(refund_lines.line_amount_minor_units) = refunds.total_amount_minor_units` for every refund, verified in the domain layer at insert time inside the same transaction, and asserted by tests. (Not a database CHECK: Postgres cannot express a cross-row aggregate constraint without a trigger, and a trigger here would add a mechanism for a rule one transaction already owns) |
| I-6 | Every `refund_lines.line_currency_code` equals its refund's `total_currency_code`, which equals the payment's `charge_currency_code`, which equals the booking's `price_currency_code`. Enforced by a CHECK on format, by the domain layer on equality, and by `REFUND_CURRENCY_MISMATCH` at the API |
| I-7 | A `failed` refund contributes to **neither** sum — its reservation is released the moment it reaches `failed`, which is precisely why AC-7 must never mark an ambiguous outcome `failed` |
| I-8 | A `completed` refund is **immutable**: its amount, currency, lines, reasons and provider reference can never change. Enforced by `refunds_completed_immutable_trg` (below) |

**Booking and payment status follow the money, and only when it is fully returned.** When
`completedRefunded` reaches `captured`, the payment transitions `captured → refunded` (or
`partially_refunded → refunded`) and the booking transitions to `refunded` via
`applyBookingTransition(..., actorRole: 'system')`. A **partial** refund transitions the payment
`captured → partially_refunded` and leaves `bookings.status` **unchanged** — `refunded` means fully
refunded, and a partially refunded booking is not a cancelled one.

### Idempotency and concurrency (AC-8)

- **Key.** `Idempotency-Key` is **required** on refund creation, read and validated by spec 015's
  existing `requireIdempotencyKey()`. The fingerprint is `idempotencyFingerprint()` over the
  canonical request body — `{ amountMinorUnits, currencyCode, reason, source }` — so a retry that
  serializes the same values in a different property order is recognised as the same request.
- **Scope.** `UNIQUE (payment_id, idempotency_key)`. Scoped per payment, never globally, matching
  spec 015/018/020/021.
- **Lock ordering.** `bookings → payments → refunds`, extending spec 021's fixed order. A provider
  call is **never** made inside a transaction, exactly as spec 021 established.

| Situation | Behaviour |
|---|---|
| Same key, same fingerprint | Replay the stored refund with `200`. **No** second provider call |
| Same key, different fingerprint | `409 IDEMPOTENCY_KEY_CONFLICT` (re-exported from `lib/requests/errors.ts`) |
| Two concurrent identical requests (same key) | The `UNIQUE` index admits one; the loser catches the unique violation and replays the winner's row. Exactly one provider call |
| Two concurrent **different** requests that together exceed `remainingRefundable` | Serialized by the `FOR UPDATE` lock on `payments`: the first commits its reservation, the second re-evaluates I-2 under the lock and is rejected `422 REFUND_EXCEEDS_CAPTURED_AMOUNT` (AC-8) |
| Retry after provider timeout / ambiguous outcome | Refused `409 REFUND_ALREADY_PROCESSING`. The existing refund stays `processing` and is resolved by the sweep, never by a second provider call (AC-7) |
| Retry after `failed` | Allowed, as a **new** refund row with a fresh key. The failed row is retained, immutable, as the record of that attempt |
| Already `processing` (any new request against the same payment while one is in flight) | Permitted **only** if I-2 still holds with the in-flight amount counted; otherwise `422 REFUND_EXCEEDS_CAPTURED_AMOUNT` |
| Already `completed` and `completedRefunded = captured` | `422 ALREADY_FULLY_REFUNDED` |

**Three-phase execution**, identical in shape to spec 021 §3 "Transaction and lock ordering":

| Phase | In a transaction? | What happens |
|---|---|---|
| 1 — reserve | yes | lock the booking, then the payment `FOR UPDATE`; consult the eligibility gate (automatic path) or verify the `AdminAction` is `Approved` (override path); evaluate I-2; insert the `refunds` row `requested` with its `refund_lines`; write the history row; **commit** |
| 2 — call | no | one `provider.refund()` call carrying the idempotency key. The refund is moved `requested → processing` in its own short transaction immediately before the call, so a crash mid-call is indistinguishable from an ambiguous outcome and is handled by the same recovery path |
| 3 — record | yes | re-lock in the same order; apply the outcome conditionally on the `version` read in phase 1; on `refunded` → `completed`, on definitive `failed` → `failed`, on `unknown` → **leave `processing`**; write the history row; transition the payment and, if fully refunded, the booking; **commit** |

### Provider ambiguity and recovery (AC-7)

| Provider result | Refund status | Reservation | Next |
|---|---|---|---|
| `refunded` | `completed` | consumed | payment/booking status updated; `reconciliation_state = 'pending'`; notification port `refund_completed` |
| `failed` (definitive code) | `failed` | released | failure code recorded; notification port `refund_failed`; retryable as a new refund |
| timeout / transport error / `unknown` | stays `processing` | **held** | resolved by the sweep; no second `refund()` call is ever issued for this row |

`GET /api/v1/cron/refund-reconcile-sweep` — a new cron route using the **existing** Vercel Cron
mechanism and bearer `CRON_SECRET`, scheduled `* * * * *` like `/cron/payment-sweep`. It selects
`processing` refunds `FOR UPDATE SKIP LOCKED` and calls `provider.getRefundStatus(refundReference)`,
which is a **read**, so it can never double-refund. A refund whose `refundReference` is `null` (the
provider never got far enough to issue one) is resolved by calling `getRefundStatus` against the
payment's reference where the adapter supports it, and otherwise stays `processing` and is
**escalated for manual finance review** after `REFUND_AMBIGUITY_ESCALATION_MINUTES` (default 60) —
it is never auto-failed and never auto-retried, because both would risk either stranding the
customer's money or refunding twice. The sweep is idempotent: the next minute's run is the retry.

### Admin override (AC-3) — the threshold, resolved

The draft left "large refunds require second-admin approval" with an **Open** threshold. Spec 009's
model has **no amount dimension**: risk tier is a column on `permissions`, keyed by
`(role, resource, action)` — `lib/admin-rbac/permissions.ts` resolves it and
`lib/admin-rbac/actions.ts` routes `low`/`medium` straight through and `high`/`critical` into the
`AdminAction` approval flow. Inventing an amount threshold would mean inventing a mechanism spec 009
does not have.

**Resolution: the risk tier is carried by the action, not by the amount.** This spec's migration
seeds, for `finance_admin` and `super_admin` only:

| resource | action | risk tier | Effect |
|---|---|---|---|
| `refunds` | `read` | `low` | Finance Admin may list and inspect refunds immediately |
| `refunds` | `override` | `high` | **Every** override routes through spec 009's approval flow — a second, distinct, authorized admin must approve before execution |

Master spec §70 lists "Large refund" as *potentially sensitive* and says high risk means
"second-admin approval **where appropriate**" — it mandates no numeric threshold. Treating every
manual refund override as high-risk satisfies §70 strictly, removes an implementation-blocking
open question without inventing a number, and is simpler to reason about than a boundary customers
and admins would inevitably probe. A later spec that genuinely needs an amount-tiered exemption
must add the amount dimension to **spec 009's** model, not to this one.

| Question | Answer |
|---|---|
| Who may initiate | An admin holding `refunds/override` — seeded to `finance_admin` and `super_admin`. Anyone else: `403 FORBIDDEN` |
| Who may approve | A **different** admin who also resolves `refunds/override` — enforced by spec 009's `decideAction()`, not re-implemented here |
| Must initiator ≠ approver | Yes. `409 SELF_APPROVAL_NOT_ALLOWED`, already enforced by `decideAction()` |
| `high` behaviour | `authorizeAndInitiate()` returns `pending_approval` with an `adminActionId`. **No refund row is created and no provider call is made.** The API answers `202` with the `adminActionId` |
| Approved | The approving admin's decision moves the `AdminAction` to `Approved`. Execution then calls `executeApprovedAction()` (`Approved → Executed`) and runs phases 1–3. A refund attempted while the action is still `Pending` is `422 APPROVAL_REQUIRED` (spec 009's existing status — **the draft's `403` is wrong**) |
| Rejected | `AdminAction` becomes `Rejected`. No refund row, no provider call, ever. A later attempt needs a new override request |
| Duplicate / concurrent approval | Spec 009's conditional `UPDATE ... WHERE status = 'Pending'` admits one; the loser gets `409 APPROVAL_NOT_ELIGIBLE`. Not re-implemented here |
| Reason | Required on initiation (master spec §68) and carried into spec 009's audit record and onto the refund's line reason |
| Audit | Entirely spec 009's `recordAdminAuditEvent` — `action_created`, `action_approved`/`action_rejected`, `action_executed` — plus this spec's own `refunds_status_history`. The refund row stores `admin_action_id`, so the approval chain is reachable from the refund and vice versa |
| Authorization/mode | Admin routes follow the repository's existing admin route convention (`requireSession` + `requireCsrf` + spec 009 permission resolution). Emergency bypass is **not** offered by this spec: `authorizeAndInitiate` is never called with `emergencyBypass: true` from here |

### Refund lines (AC-2)

- A `refund_lines` row belongs to **exactly one** `refunds` row — one refund record, one execution
  attempt, one provider call. Multiple partial refunds against one payment are **multiple `refunds`
  rows**, each with its own lines, own idempotency key, own provider reference and own history.
- Lines are **append-only and immutable**, enforced by `refund_lines_append_only_trg`. The reason
  recorded on a line is the reason that was decided — by spec 023's eligibility decision or by the
  admin's override reason — and can never be edited afterwards.
- `total_amount_minor_units` is **not** derived at read time; it is stored on the refund and must
  equal the sum of its lines (I-5), so the authoritative total cannot drift from its explanation.
- A `completed` refund can **never** be edited, by any code path: `refunds_completed_immutable_trg`
  rejects any `UPDATE` to a `completed` row other than the two reconciliation columns spec 024
  owns. A correction after completion is a **new** financial record, never a rewrite.

### Reconciliation seam (AC-4) — spec 024 owns the ledger

Spec 022 implements no ledger, writes no `payouts`/`payout_methods` row and computes no fee. What it
produces is a **durable fact**:

- `refunds.reconciliation_state` ∈ `pending | reconciled`, default `pending`, plus
  `reconciled_at timestamptz`. Spec 022 sets `pending` when a refund completes and **never** writes
  `reconciled` — that column is spec 024's only write into this table.
- `refunds_reconciliation_idx` on `(reconciliation_state, completed_at)` is the index spec 024's
  consumer reads.
- A port, `RefundReconciliationSink`, with an inert default, lets spec 024 react promptly when it
  ships. The **durable column remains the source of truth**: if the port is inert, throws, or the
  process dies, the fact survives and spec 024 picks it up on its next pass. The port is a latency
  optimisation, never the record.

**If reconciliation is delayed**, the refund is still financially `completed` — provider
confirmation is what makes it so, not the ledger. The contract spec 024 must honour, stated here
because this spec owns the data that makes it checkable: **a provider must not be reported as paid,
or advanced to payout-eligible, for an amount carried by a refund whose `reconciliation_state` is
still `pending`.** Unreconciled refunds older than a threshold are alerted on (§9), never silently
dropped.

### Notification seam (§15)

Spec 026 owns notification infrastructure and has not shipped; the `notifications` table is still a
spec 003 skeleton. This spec therefore ships a **port** with an inert default and no delivery
mechanism of its own:

```typescript
// lib/refunds/notifications.ts
export type RefundNotificationEvent =
  | { kind: 'refund_completed'; refundId: string; bookingId: string; recipientUserId: string }
  | { kind: 'refund_failed'; refundId: string; bookingId: string; recipientUserId: string }
  | { kind: 'refund_approval_required'; adminActionId: string }
  | { kind: 'refund_approval_decided'; adminActionId: string; decision: 'approved' | 'rejected' };

export type RefundNotificationSink = (event: RefundNotificationEvent) => Promise<void>;
```

The default is a no-op that logs a structured line. Emission is **fire-and-forget after the
transaction commits**: a notification failure must never roll back or fail a completed refund.

Repository conventions: `app/api/v1/**/route.ts`, path parameters read from the URL with a local

`session → CSRF → active mode / admin permission → rate limit → Idempotency-Key`.

| Method | Route | Auth / mode | Success | Notes |
|---|---|---|---|---|
| `POST` | `/api/v1/bookings/{id}/refunds` | session, `customer` mode, booking's customer | `201 ApiResponse<RefundDto>` (`200` on idempotent replay) | CSRF; `Idempotency-Key`; rate-limit `payment`; consults the eligibility gate — **never** an amount chosen by the client |
| `GET` | `/api/v1/bookings/{id}/refunds` | session, either participant in their own mode | `200 ApiResponse<RefundDto[]>` | newest first; provider sees amounts and status, never provider references or failure codes |
| `POST` | `/api/v1/admin/refunds` | admin holding `refunds/override` | `202 ApiResponse<RefundOverrideDto>` when approval is pending; `201 ApiResponse<RefundDto>` once executed | CSRF; `Idempotency-Key`; `reason` required; body names `bookingId`, `amountMinorUnits`, `currencyCode` |
| `GET` | `/api/v1/admin/refunds` | admin holding `refunds/read` | `200 PagedResponse<RefundDto>` | spec 004's `parsePageParams`/`buildPage`; filterable by `status` and `reconciliationState` |
| `GET` | `/api/v1/cron/refund-reconcile-sweep` | `Bearer ${CRON_SECRET}` | `200` | not a browser route: no session, no CSRF, no rate limit |

**Approval listing and decisions use spec 009's existing routes** — `GET /api/v1/admin/approvals/pending`
and `POST /api/v1/admin/approvals/{actionId}/approve|reject`. This spec adds none of its own.

**Privacy-safe `404`.** A caller who is not a participant on the booking — or an admin without
`refunds/read` addressing a refund id — gets `404 REFUND_NOT_FOUND`, never `403`, so ids cannot be
probed by observing a different status. `403 FORBIDDEN` is reserved for a participant in the wrong
active mode and for an admin lacking the permission on a non-id-bearing route.

`RefundDto` deliberately carries **no** `providerReference`, `refundReference`, `failureCode`,
`failureReason`, `idempotencyKey` or `initiatedByUserId`. The customer-facing failure message is
master spec §105's wording, not the provider's string. The draft's `approvedByAdminId` is removed
from the participant-facing DTO: the approval chain is admin data, reachable from `adminActionId`
on the admin surface only.

**The customer route takes no amount.** A client-supplied refund amount would be a client deciding
how much money to send itself; the amount comes from spec 023's eligibility decision, server-side,
always. Only the admin override route accepts an amount, and only behind two-admin approval.

### Error codes

None is in spec 004's shared `API_ERROR_CODES` map, so each passes `options.status` explicitly —
the pattern specs 005/016/020/021 already follow. Codes owned by an earlier spec are
**re-exported, never redefined**.

| HTTP | `code` | When |
|---|---|---|
| `404` | `REFUND_NOT_FOUND` | no such booking/refund, **or** the caller is not a participant (deliberately indistinguishable) |
| `422` | `PAYMENT_NOT_CAPTURED` | the booking's payment was never captured, so there is nothing to refund |
| `422` | `BOOKING_NOT_REFUNDABLE` | the booking is in a status from which no refund is possible (e.g. `pending`, `failed`) |
| `422` | `REFUND_NOT_ELIGIBLE` | the eligibility gate declined, or is unavailable (`details.reason`) |
| `422` | `REFUND_ELIGIBILITY_INVALID` | the gate returned `eligible: true` with a missing or malformed amount, currency or reason |
| `422` | `REFUND_AMOUNT_INVALID` | non-integer, zero or negative amount, or lines that do not sum to the total |
| `422` | `REFUND_CURRENCY_MISMATCH` | the refund currency differs from the booking's |
| `422` | `REFUND_EXCEEDS_CAPTURED_AMOUNT` | the request exceeds `remainingRefundable`; `details` carries `remainingRefundableMinorUnits` |
| `422` | `ALREADY_FULLY_REFUNDED` | `completedRefunded` already equals `captured` |
| `409` | `REFUND_ALREADY_PROCESSING` | a retry against a refund whose provider outcome is still in flight or unknown (AC-7) |
| `409` | `IDEMPOTENCY_KEY_CONFLICT` | re-exported from `lib/requests/errors.ts` — same key, different fingerprint |
| `409` | `CONFLICT` | stale `version` on a refund (spec 003 AC-6) |
| `422` | `APPROVAL_REQUIRED` | execution attempted while the `AdminAction` is still `Pending`. Re-exported from `lib/admin-rbac/errors.ts` — **422, not the draft's 403** |
| `409` | `APPROVAL_NOT_ELIGIBLE` | re-exported from spec 009 |
| `409` | `SELF_APPROVAL_NOT_ALLOWED` | re-exported from spec 009 |
| `403` | `FORBIDDEN` | wrong active mode, or admin lacking `refunds/override` / `refunds/read` |
| `503` | `PAYMENT_PROVIDER_UNAVAILABLE` | re-exported from `lib/payments/errors.ts` — AC-10's production guard, or an adapter outage. No refund row is created |

## 4. Data model changes

**`refunds` and `refund_lines` already exist** as spec 003 baseline skeletons with their FKs and
indexes. This spec **alters** them and adds two small state-machine tables. `0001_baseline_schema.sql`
is immutable (`npm run check:schema-checksum`) and is not touched.

`baseColumns()` already supplies `id`, `created_at`, `updated_at` and `version`, so those are not
listed as additions. Money follows spec 003 AC-1's `<base>_amount_minor_units` +
`<base>_currency_code` convention via `moneyColumns()`.

### Refund status machine

`refunds_status_ck`: `status in ('requested','processing','completed','failed')`.

Seeded into `refunds_status_transitions`, and **only** these:

```
requested  → processing
processing → completed
processing → failed
```

`completed` and `failed` have no outgoing transition. `requested → failed` is deliberately absent:
nothing can fail before the provider has been asked, and a refund rejected before phase 2 is never
inserted in the first place.

`refunds_status_transition_trg` attaches spec 003's **existing** `enforce_status_transition()`
function to `refunds` — the same one already on `requests`, `offers`, `bookings`, `payments` and
`payouts`. No new trigger function is written.

### Migration

- **Name:** `0018_add_refunds.sql`, with a hand-written `0018_add_refunds_down.sql` — the
  repository's convention (`0012`–`0017` all follow it; drizzle-kit generates no down migration, and
  the down file carries no `_journal.json` entry so `npm run db:migrate` never applies it).
  `0017_add_payment_processing_protection` is the current head, so `0018` is the next number.
- **Precondition guard:** `RAISE EXCEPTION` unless `refunds` and `refund_lines` are empty — the same
  `DO $$` guard `0016` and `0017` use, which is what makes `NOT NULL` columns without defaults safe
  to add directly.
- **Reversible:** yes. The down migration drops only what `0018` added, deletes only the
  `payments_status_transitions`, `bookings_status_transitions` and `permissions` rows `0018`
  inserted, and touches no other table.
- **Backfill required:** no (both tables are empty).
- **Downtime:** none.
- **Reviewed SQL:** hand-reviewed in PR; `npm run check:schema-baseline` must pass.

### Retention and privacy

- **No payment-instrument data is stored.** There is no PAN, CVV, expiry, IBAN, wallet or token
  column in this spec, and the extended adapter interface has no parameter that could carry one.
- **Retention (spec 008).** `refunds`, `refund_lines` and `refunds_status_history` are financial
  records, retained regardless of account deletion under spec 008's **existing** rule —
  `lib/privacy/deletion.ts` already names `Refund` among the retained financial entities, and every
  FK here is `restrict`. No new retention mechanism, sweep or policy is introduced.
- **Export boundary (spec 008).** `lib/privacy/export.ts` currently exports refunds as
  `{ id, paymentId, createdAt }`. This spec extends that projection with `bookingId`, `status`,
  `totalAmountMinorUnits`, `totalCurrencyCode`, `completedAt`, and each line's
  `lineAmountMinorUnits`, `lineCurrencyCode` and `reason`. **Never exported:**
  `provider_reference`, `refund_reference`, `failure_code`, `failure_reason`, `idempotency_key`,
  `idempotency_fingerprint`, `admin_action_id`, `initiated_by_user_id` and
  `eligibility_decision_ref` — provider handles, internal reconciliation data, and admin/security
  detail beyond the user's own record. A provider's export shows their own bookings' refund amounts
  and status, never the customer's payment detail or any approval chain.

## 5. UI states

**There is no WebSocket layer in this repository** — specs 018, 019 and 020 all say so, and spec
020's booking screens poll (`BOOKING_POLL_MS = 10_000` in `app/bookings/booking-client.ts`,
refetching on that cadence and on window focus). The draft's "polls/updates via WebSocket" is
removed: refund status uses **that same existing polling mechanism**, and no realtime architecture
is introduced.

### Customer

Refund status is a section on the existing booking detail screen, `app/bookings/[id]`, beside the
payment section spec 021 added. No new customer route.

| State | Behaviour |
|---|---|
| **Loading** | skeleton within the section; polling continues while any refund is `requested`/`processing`, and stops once every refund is terminal |
| **Empty** | a booking with no refunds renders no refund section at all — not an empty-state card |
| **Processing** | explicit "Refund in progress" with the exact amount and currency. Never "Refunded" before the provider has confirmed it (master spec §132.7) |
| **Error** | a `failed` refund states plainly that it did not complete, that no money was returned by this attempt, and what happens next — "Contact support" — never a dead end and never a bare provider code |
| **Success** | the completed refund shows amount, currency, each line's reason, and the completion instant |

### Finance Admin

`app/admin/operations/refunds` — a new page under the existing `app/admin/operations` area, whose
current `PlaceholderPage` already links out to spec 009's approvals flows and gains a "Refunds"
link. Override initiation requires a reason before submission (master spec §68) and shows the
approval-chain status explicitly: pending second-admin approval, approved, rejected, executed.
Approving and rejecting happen on spec 009's existing `app/admin/approvals` screen — this spec adds
no second approval UI.

**Components.** Built from the existing design system — `Table`, `Card`, `Badge`, `Button`,
`ConfirmDialog`, `ErrorState`, `Skeleton` from `@/components`, and tokens from
`app/styles/apuriva-tokens.css`. The draft's `packages/ui` path does not exist in this repository.
No design-system token, primitive or `ui/` file is added or changed; Home and the global design
system are untouched. No brand mark is added — the nav shell provides the one intentional
placement. No visual redesign of any existing screen is performed.

**Route(s):** `app/bookings/[id]` (mounts `app/bookings/_components/RefundSection.tsx`),
`app/admin/operations/refunds` (new, linked from the existing Operations page).

**One implementation note on the customer section:** it treats anything other than an actual array
as "no refunds" and stops polling. A `404`, an error envelope or an unexpected shape will not start
answering usefully because the page asks again every ten seconds, and an endpoint that is failing
should not be hammered by every open booking screen.

- **Cancellation-policy rules and fee calculation** — spec 023. This spec ships the eligibility
  port and executes what it is handed.
- **Payout ledger, earnings math, payout lifecycle** — spec 024, including every `payouts*` baseline
  table. This spec produces only the `reconciliation_state` fact.
- **Notification delivery, templates, channels and preferences** — spec 026. This spec ships only
  the sink port.
- **Dispute creation or resolution** — spec 031. A dispute that resolves into a refund calls this
  spec's domain function; this spec knows nothing about disputes.
- **Payment authorization and capture** — spec 021, which remains the payment source of truth. This
  spec adds one method to its adapter interface and no second abstraction.
- **Admin RBAC, risk-tier mechanics, approval routes and the admin audit log** — spec 009. This
  spec seeds two permission rows and calls the framework.
- **Any amount-based approval threshold** — deliberately not invented; see §3 "Admin override".
- **Known spec 010/011 catalog/schema defects**, and the spec 010 OpenAPI `{categoryId}` mismatch.
- **Any change to Home, `ui/`, `app/styles/apuriva-tokens.css`, or the primitive set in
  `components/index.ts`.**

## 8. Risks and open questions

| # | Risk / question | Owner | Resolution |
|---|---|---|---|
| 1 | Refund-amount threshold that triggers second-admin approval (draft's Open question) | Platform/Finance | **Resolved** (§3 "Admin override"): spec 009's risk tier is per `(role, resource, action)` and has no amount dimension, so `refunds/override` is seeded at `high` and **every** override requires a second admin. Master spec §70 mandates no numeric threshold. No amount is invented, and nothing is left blocking |
| 2 | Spec 021's `PaymentProvider` has no refund primitive | Platform | **Resolved** (§3 "Provider seam extension"): the existing interface is **extended** with `refund`/`getRefundStatus` inside `lib/payments/provider/`, keeping one payment abstraction and one credential boundary. A second abstraction is explicitly rejected |
| 3 | A provider timeout could be mistaken for a failure and double-refund on retry | Platform | **Resolved** (AC-7, §3 "Provider ambiguity"): `unknown` is a first-class outcome; the refund stays `processing` with its reservation held; recovery is a `getRefundStatus` **read** via the sweep, never a second `refund()` call; unresolved rows escalate to manual review rather than auto-failing |
| 4 | Concurrent refunds could together exceed the captured amount | Platform | **Resolved** (AC-8, I-2): admission is evaluated under `SELECT ... FOR UPDATE` on the `payments` row in the same transaction that inserts the reservation — a database serialization, not an application-only check |
| 5 | `refunds` has no status machine in the baseline | Platform | **Resolved** (§4): create `refunds_status_transitions` and attach spec 003's **existing** `enforce_status_transition()` function. No new mechanism |
| 6 | Spec 023 does not exist, so automatic refunds have no policy source | Platform | **Resolved** (§3 "Eligibility"): an inert-default port. With no policy registered nothing is automatically refundable, which is correct rather than a stub; the admin path is unaffected |
| 7 | Spec 024 does not exist, so reconciliation has no consumer | Platform | **Resolved** (§3 "Reconciliation seam"): a durable `reconciliation_state` column is the record; the sink port is a latency optimisation. A delayed consumer cannot make a refund incorrect, only unreconciled — and unreconciled refunds are alerted on |
| 8 | Spec 026 does not exist, so notifications have no delivery mechanism | Platform | **Resolved** (§3 "Notification seam"): an inert-default sink, emitted after commit, whose failure can never roll back a completed refund |
| 9 | A partial refund might be read as cancelling the booking | Product/Platform | **Resolved** (§3 "Financial invariants"): `bookings.status = 'refunded'` means **fully** refunded. A partial refund moves the payment to `partially_refunded` and leaves the booking untouched |
| 10 | Multi-currency refunds | Product | **Out of scope, named rather than invented**: I-6 makes a cross-currency refund impossible rather than silently wrong. Multi-currency is a later product decision, as it is in spec 021 |

No open question remains that blocks implementation.

### Decided during implementation

Five points the finalized contract left implicit, settled while building and recorded here so the
document matches the code:

| # | Point | Decision |
|---|---|---|
| 1 | `applyPaymentTransition()` guards against pairs spec 021 does not own, so spec 022 could not perform its three | A `registerPaymentTransitions` extension registry was added to `lib/payments/state-machine.ts`, mirroring the `registerBookingTransitions` one spec 021 already added to `lib/bookings`. `SPEC_021_PAYMENT_TRANSITIONS` and `isAllowedPaymentTransition()` are untouched, so spec 021's own tests — which assert the refund pairs are NOT spec 021's — pass unchanged. The database remains the real authority |
| 2 | A booking with no payment row reported `REFUND_NOT_FOUND` | It now reports `422 PAYMENT_NOT_CAPTURED`. That booking exists and the caller may see it; "nothing was ever captured" is the accurate answer, and `404` stays reserved for a booking the caller may not see |
| 3 | A fully refunded payment/booking reported "not captured" / "not refundable" | `refunded` is admitted past both guards so the specific `422 ALREADY_FULLY_REFUNDED` surfaces. Those rows WERE captured and WERE refundable; the precise error is the useful one |
| 4 | Whether a customer's same-key retry conflicts when the policy decision changed | It **replays**. The customer route carries no amount, so two calls under one key are the same client request however the server-side policy moved; replaying is structurally incapable of refunding twice, which a "the policy changed, refund again" reading would not be. The conflicting-fingerprint path is exercised on the admin route, where the client does supply an amount |
| 5 | `authorizeAndInitiate` returning `permitted` or `emergency_bypass_executed` for an override | Both are **refused** with `422 APPROVAL_REQUIRED` rather than honoured. C-5 requires a real `admin_action_id` from a real approval chain, and spec 009's `AdminAction.risk_tier` admits only `high`/`critical` — so there is no honest row to write for a lower-tier override. A misconfigured seed therefore fails closed instead of silently disabling AC-3's four eyes |

## 9. Rollout

- **Feature flag:** none. Refunds are core. The provider adapter remains swappable through spec
  021's existing `PAYMENT_PROVIDER` variable; no feature-flag system is introduced (spec 041 owns
  that).
- **Environment:** one variable added to `.env` / `.env.example`, kept in parity by
  `npm run check:env` — `REFUND_AMBIGUITY_ESCALATION_MINUTES` (default 60, §3 "Provider ambiguity").
- **Migration order:** `0018` ships with the code. Because the refund routes depend on its columns,
  migration and deploy are one unit.
- **Cron:** `/api/v1/cron/refund-reconcile-sweep` added to `vercel.json` at `* * * * *`, matching
  `/cron/payment-sweep` — same mechanism, same bearer `CRON_SECRET`, no new scheduler.
- **Rollback — and what "rollback" can and cannot mean for money.** The draft said "revert deploy",
  which is unsafe wording for a financial system: **a refund the provider has already executed
  cannot be reversed by any code change.** The actual safe procedure is:
  1. **Roll the code back, not the money.** Reverting the deploy stops new refunds being created;
     it does not and must not attempt to undo executed ones.
  2. **Do not apply the down migration while any refund row exists.** `0018`'s down migration
     deletes refund rows and is safe **only** before the first refund ships, which is why it is
     gated on empty tables. Once real refunds exist, rolling the schema back would destroy financial
     records that spec 008 requires be retained; the correct response to a defect is a forward fix.
  3. **The provider stays authoritative.** Any refund left `processing` across a rollback is
     resolved by `getRefundStatus` when the sweep next runs, on whatever code version is deployed —
     `processing` is never reinterpreted as failed, and no duplicate `refund()` call is possible
     because recovery is a read.
  4. **Reconciliation is replayable.** `reconciliation_state = 'pending'` is durable, so a rollback
     across the spec 024 boundary loses no deduction; it is picked up on the next pass.
- **Observability (master spec §117):** structured logs for `refund.requested`, `refund.processing`,
  `refund.completed`, `refund.failed`, `refund.outcome_unknown`, `refund.escalated` and
  `refund.override_initiated`, each carrying `correlationId`, `refundId`, `bookingId` and `status` —
  never a provider payload, a provider reference, or an amount tied to an identifiable person in a
  log line. Alert on: refund failure rate; any refund `processing` for longer than the escalation
  threshold; any refund `reconciliation_state = 'pending'` beyond a reconciliation SLA; and override
  frequency, with unusual spikes routed to Trust & Safety (master spec §68).
