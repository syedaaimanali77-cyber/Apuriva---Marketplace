## 1. Problem statement

**Today:** No refund mechanism exists. Master spec §49 requires full and partial refunds, both
automatic policy-driven refunds and admin-controlled overrides where permitted, with a
`Requested → Processing → Completed/Failed` status flow, reconciled against provider earnings,
and fully audited.

**Who is affected:** Customers owed money back; providers whose earnings must reconcile
correctly against any refund; Finance Admins who approve overrides.

**Why it matters now:** Depends on payment processing (021) existing; feeds cancellation policy
(023) and payout reconciliation (024).

**Success looks like:** A refund (full or partial) can be issued automatically per policy or by
a Finance Admin override, always reconciles against the provider's earnings ledger, and is
fully audited end to end.

## 2. Acceptance criteria

| # | Criterion |
|---|---|
| AC-1 | **Given** a policy condition that triggers an automatic refund (e.g. cancellation within the free window) **When** met **Then** the refund is issued without manual intervention and moves `Requested → Processing → Completed` |
| AC-2 | **Given** a partial refund **When** issued **Then** the exact amount and reason are recorded as `RefundLine` entries, and the sum never exceeds the original captured payment |
| AC-3 | **Given** a Finance Admin override outside normal policy **When** requested **Then** it follows the risk-tiered approval flow from spec 009 (large refunds require second-admin approval, per master spec §70) |
| AC-4 | **Given** a completed refund **When** reconciled **Then** the provider's earnings ledger (spec 024) reflects the reduction accurately — never leaving a provider "paid" for an amount that was refunded |
| AC-5 | **Given** a refund attempt on an already-fully-refunded payment **When** attempted **Then** it is rejected with `422`, not silently processed as a duplicate |
| AC-6 | **Given** a failed refund (provider-side failure) **When** it occurs **Then** status becomes `Failed`, the customer and Finance Admin are notified, and it is retryable |

## 3. API contract

### Endpoints

| Method | Route | Auth | Success | Notes |
|---|---|---|---|---|
| `POST` | `/api/v1/bookings/{id}/refunds` | session (customer, triggers policy check) or admin (Finance) | `201` `ApiResponse<RefundDto>` | policy-driven path validates eligibility; admin path requires reason + risk-tier approval |
| `GET` | `/api/v1/bookings/{id}/refunds` | session (participant) or admin | `200` `ApiResponse<RefundDto[]>` | |
| `GET` | `/api/v1/admin/refunds/pending-approval` | admin (Finance) | `200` `PagedResponse<RefundDto>` | high-risk refunds awaiting second admin |

### Request and response types

```typescript
// packages/types/src/refunds.ts
export interface RefundDto {
  id: string;
  bookingId: string;
  status: 'requested' | 'processing' | 'completed' | 'failed';
  totalAmountMinorUnits: number;
  currencyCode: string;
  lines: Array<{ amountMinorUnits: number; reason: string }>;
  isOverride: boolean;
  approvedByAdminId?: string;
}
```

### Error codes

| HTTP | `code` | When |
|---|---|---|
| `422` | `REFUND_EXCEEDS_CAPTURED_AMOUNT` | requested refund total exceeds what was actually captured |
| `422` | `ALREADY_FULLY_REFUNDED` | duplicate refund attempt on a fully refunded payment |
| `403` | `APPROVAL_REQUIRED` | high-risk override attempted without second-admin approval (ties to spec 009) |

## 4. Data model changes

### Entities

| Entity | Change | Fields |
|---|---|---|
| `Refund` | new | `id uuid pk`, `payment_id uuid fk->Payment`, `booking_id uuid fk->Booking`, `status text`, `total_amount_minor_units integer`, `currency_code text`, `is_override boolean`, `initiated_by_type text` (system/admin), `initiated_by_id uuid nullable`, `created_at`, `updated_at` |
| `RefundLine` | new | `id uuid pk`, `refund_id uuid fk->Refund`, `amount_minor_units integer`, `reason text` |

Refunds reference `AdminAction`/`AdminActionApproval` (spec 009) when `is_override = true` and
`risk_tier` is high/critical.

### Migration

- **Name:** `AddRefundTables`
- **Reversible:** yes
- **Backfill required:** no
- **Downtime:** none
- **Reviewed SQL:** generated, reviewed in PR

### Retention and privacy

Financial records, retained per legal/audit policy regardless of account deletion (spec 008).

## 5. UI states

| State | Behaviour |
|---|---|
| **Loading** | refund status polls/updates via WebSocket or refresh, shows "Processing" state explicitly |
| **Empty** | booking with no refunds shows nothing extra (not applicable as an empty state concern) |
| **Error** | failed refund shows reason and next steps (contact support), not a dead end |
| **Success** | completed refund shown with amount, reason, and reconciliation reference |

Admin override UI requires reason entry before submission (master spec §68) and shows the
approval-chain status clearly.

**Route(s):** `apps/web/app/bookings/[id]` (refund status section), `apps/web/app/admin/operations/refunds`
**Shared components used/added:** `packages/ui` `Table`, `ConfirmDialog`

## 9. Rollout

- **Feature flag:** none.
- **Migration order:** schema ships with code.
- **Rollback:** revert deploy; refunds are payment-provider-authoritative, reconciled
  independent of app-code version.
- **Observability:** refund volume, failure rate, and override frequency monitored (master
  spec §117); unusual override spikes alerted to Trust & Safety.
